# Data Export: Ontologies and Diagrams

> Status: **proposal, not built.** High-level design only. Czech version:
> [`DATA_EXPORT_CS.md`](./DATA_EXPORT_CS.md).

## What problem this solves

The application must make available its diagram data and its draft and published ontologies,
including their metadata, as open data. The files are offered for download and can be catalogued
in NKOD.

The export consists of **two JSON-LD files**: one with all ontologies and their concepts, one with
all diagrams. Each file describes itself (export time, completeness, per-ontology metadata), so
there is no manifest. Because the files are JSON-LD with a fixed `@context`, the NKOD dataset
metadata does not have to be generated by ISMD; it is written once by hand.

## Why a new endpoint

The data is split across two stores, and neither existing surface covers it.

| Option | Why it is not enough |
|---|---|
| **Fuseki / SPARQL directly** | Diagrams and the ontology metadata (slug, publication state, timestamps) exist only in PostgreSQL. The Fuseki service also exposes `update`, `upload` and `gsp-rw` next to `query`, so it cannot be opened to a consumer as it is. |
| **Existing REST endpoints** | A consumer would need one call for the ontology list, one download per ontology, one call for the diagram list and one detail call per diagram. The ontology download is refused for ontologies with validation errors when the download restriction is on, the list model carries user and comment fields, and the diagram detail is the fat read that includes staged pending edits. |

The export reuses the existing building blocks (`OntologyDownloadService`, the diagram
repositories) behind one controller that applies the export rules in one place.

## Scope

| Included | Excluded |
|---|---|
| Every ontology, draft and published, regardless of validation state (see [Pending decisions](#pending-decisions)) | Comments |
| Ontology metadata from PostgreSQL | Any user information, including the owner id |
| Ontology content as cleaned OFN JSON-LD (the same output as the JSON-LD ontology download) | Staged pending diagram edits (`diagram_pending_edits`) |
| Concept metadata from PostgreSQL, merged into each concept | Validation reports |
| Every diagram with its stored layout | Outbox, reconciler and other operational data |
| | NKD, NKOD, RPP and e-Sbírka data |

## Endpoints

```
GET|HEAD|OPTIONS /api/export/slovniky.jsonld
GET|HEAD|OPTIONS /api/export/diagramy.jsonld
```

Each file is a separate NKOD distribution.

| Aspect | Value |
|---|---|
| Authorization | Public (`permitAll()` matchers for both paths in `SecurityConfig`), because an NKOD distribution must be downloadable without login. Depends on pending decision 1. |
| Response | `application/ld+json; charset=utf-8`, `Content-Disposition: attachment; filename="slovniky.jsonld"` (or `diagramy.jsonld`), `ETag`, `Last-Modified` |
| `GET` | Serves the cached file. If the data changed since the file was built, the file is rebuilt first; this can take several seconds. Supports `If-None-Match` / `If-Modified-Since` → `304`. |
| `HEAD` | **Must answer within 3 s and never builds the file.** See [HEAD and OPTIONS](#head-and-options). |
| `OPTIONS` | Answered by Spring (`Allow`, CORS preflight) without reaching the controller. |
| Concurrency | Single-flight per file: concurrent `GET`s during a rebuild wait for the same build. No `409`. |

### HEAD and OPTIONS

By default Spring answers `HEAD` by running the `GET` handler and discarding the body, which would
make `HEAD` as slow as a full rebuild. The controller therefore maps `HEAD` explicitly:

1. Compute the current **fingerprint** of the file's source data with one PostgreSQL query (see
   [Cache](#cache)). This takes milliseconds and does not touch Fuseki.
2. If the cached file matches the fingerprint, return its `Content-Type`, `Content-Length`,
   `ETag` and `Last-Modified`.
3. Otherwise return `Content-Type` and `ETag` (the new fingerprint) without `Content-Length`, and
   start a background rebuild so the following `GET` is fast.

`OPTIONS` needs no code, only a test that it answers without calling the builder.

### Cache

The backend runs as a single instance, so the cache is a file on local disk plus an in-memory
record per export file: fingerprint, build time, size.

- **Fingerprint:** a hash over `(id, updated_at)` of every row that feeds the file (ontologies and
  concepts for `slovniky.jsonld`; diagrams for `diagramy.jsonld`, plus ontology IRIs, which the
  diagrams reference). Hashing the full id list, not only `max(updated_at)`, also detects deletions.
  RDF-only edits bump `updated_at` through `MetadataTouchService`, so they are covered.
- **ETag** = fingerprint. **Last-Modified** = time the cached file was built.
- **Build:** written to a temporary file and moved into place only when complete, so a client
  never receives a half-built file and the HTTP status reflects the real outcome.
- **Startup:** the cache is empty after a restart; a background build runs at startup.

## File format

Both files are JSON-LD with two contexts:

```json
"@context": [
  "https://ofn.gov.cz/slovníky/2026-02-26/kompletní/kontext.jsonld",
  "<ISMD export context URL>"
]
```

- **OFN Slovníky** (published version 2026-02-26) defines the ontology and concept content:
  `iri`, `typ`, `název`, `popis`, `vytvořeno`, `aktualizováno`, `pojmy` and every concept field.
  The existing JSON-LD download already uses this context through the `draft2` URL; the two files
  are identical, and the export uses the dated URL.
- **The ISMD export context** defines everything OFN does not: the PostgreSQL metadata, the export
  record and the diagrams. Its terms come from a vocabulary describing this dataset, created once by
  hand (see pending decision 2). The term names below are provisional; the final names come from
  that vocabulary.

Each file is a top-level `@graph` array: one node per ontology (or diagram) plus one **export
record** node. The OFN JSON Schema describes a single ontology, so it validates each ontology node,
not the whole file.

Timestamps use the OFN shape `{"typ": "Časový okamžik", "datum_a_čas": "…"}` with an explicit
offset. PostgreSQL stores `createdAt` / `updatedAt` without a zone; the export attaches
`Europe/Prague`.

**No database identifiers are exported.** Ontologies and concepts are identified by IRI, a diagram
by its own IRI (see [Diagram IRI](#diagram-iri)), and a diagram node by its concept IRI.

### Export record

Present in both files; replaces the manifest's top-level fields.

```json
{
  "typ": "Export ISMD",
  "exportováno": { "typ": "Časový okamžik", "datum_a_čas": "2026-10-07T11:30:00+02:00" },
  "úplný": true
}
```

- `exportováno` marks the PostgreSQL snapshot (see [Consistency](#consistency)).
- `úplný` is `false` when at least one ontology has `stav-obsahu = FAILED`. Always `true` in the
  diagrams file.

### `slovniky.jsonld`

```json
{
  "@context": [ "https://ofn.gov.cz/slovníky/2026-02-26/kompletní/kontext.jsonld", "<ISMD>" ],
  "@graph": [
    {
      "iri": "https://slovník.gov.cz/agendový/moje-agenda",
      "typ": ["Slovník"],
      "název": { "cs": "Moje agenda" },
      "vytvořeno": { "typ": "Časový okamžik", "datum_a_čas": "2026-03-02T10:15:00+01:00" },
      "aktualizováno": { "typ": "Časový okamžik", "datum_a_čas": "2026-09-30T14:02:11+02:00" },
      "slug": "moje-agenda",
      "je-publikován": false,
      "stav-poslední-validace": "VALIDATED",
      "okamžik-poslední-validace": { "typ": "Časový okamžik", "datum_a_čas": "2026-09-30T14:02:15+02:00" },
      "stav-obsahu": "OK",
      "počet-pojmů": 42,
      "pojmy": [
        {
          "iri": "https://slovník.gov.cz/agendový/moje-agenda/pojem/žadatel",
          "typ": ["Pojem", "Třída"],
          "název": { "cs": "Žadatel" },
          "slug": "zadatel",
          "je-publikován": false,
          "je-v-tezauru": false,
          "vytvořeno": { "typ": "Časový okamžik", "datum_a_čas": "2026-03-02T10:20:00+01:00" },
          "aktualizováno": { "typ": "Časový okamžik", "datum_a_čas": "2026-09-30T14:02:11+02:00" }
        }
      ]
    },
    { "typ": "Export ISMD", "exportováno": { "…": "…" }, "úplný": true }
  ]
}
```

- The ontology node is the existing OFN JSON-LD download output (the content fields, `pojmy`
  and everything in it) with the PostgreSQL metadata added. Each concept in `pojmy` gets its
  PostgreSQL fields merged in by IRI. The former `concepts.json` is gone.
- The concept type from PostgreSQL (`TRIDA`, …) is not repeated; OFN `typ` already carries it.
- `iri` is the ontology's graph name.
- `stav-obsahu` is `OK`, `EMPTY` (the ontology has no RDF content yet) or `FAILED` (the fetch or
  the transformation failed). With `EMPTY` and `FAILED` the node carries only the PostgreSQL
  metadata; `počet-pojmů` still says how many concepts PostgreSQL knows.
- `stav-poslední-validace` is `VALIDATED`, `SKIPPED_UNAVAILABLE` or `FAILED`. It says whether the
  last validation run completed, not whether it found errors; the findings are in the validation
  report, which is not exported.

### `diagramy.jsonld`

The **stored layout**, not the projected read model the frontend receives.

```json
{
  "@context": [ "https://ofn.gov.cz/slovníky/2026-02-26/kompletní/kontext.jsonld", "<ISMD>" ],
  "@graph": [
    {
      "iri": "<diagram IRI base>/3f2c9a1e-5b7d-4c0a-9e8f-1a2b3c4d5e6f",
      "typ": "Diagram",
      "název": "Přehled",
      "slovník": "https://slovník.gov.cz/agendový/moje-agenda",
      "vytvořeno": { "typ": "Časový okamžik", "datum_a_čas": "2026-04-11T08:00:00+02:00" },
      "aktualizováno": { "typ": "Časový okamžik", "datum_a_čas": "2026-09-12T16:40:00+02:00" },
      "výřez": { "x": 0.0, "y": 0.0, "přiblížení": 1.0 },
      "uzly": [
        {
          "pojem": "https://slovník.gov.cz/agendový/moje-agenda/pojem/žadatel",
          "pozice": { "x": 120.0, "y": 80.0 },
          "sbalený": false,
          "seskupen-pod": null,
          "cizí": false,
          "zobrazené-vlastnosti": [
            "https://slovník.gov.cz/agendový/moje-agenda/pojem/jméno-žadatele"
          ]
        }
      ],
      "hrany": [
        {
          "klíč-hrany": "https://slovník.gov.cz/agendový/moje-agenda/pojem/podává",
          "body-zlomu": [ { "x": 200.0, "y": 140.0 } ]
        }
      ]
    },
    { "typ": "Export ISMD", "exportováno": { "…": "…" }, "úplný": true }
  ]
}
```

| Field | Was | Note |
|---|---|---|
| `slovník` | `ontologyIri` | IRI reference (`@type: @id`) to the ontology node in `slovniky.jsonld` |
| `pojem` | `conceptIri` | IRI reference |
| `seskupen-pod` | `parentConceptIri` | IRI reference to the concept of the node this node is grouped under, or `null` |
| `cizí` | `foreign` | The node references a concept from another ontology |
| `zobrazené-vlastnosti` | `visibleProperties` | IRI references |
| `klíč-hrany` | `edgeKey` | A string, not an IRI reference: for hierarchy edges it is a key assembled by the frontend |
| `body-zlomu` | `segments` | |
| `výřez` | `viewport` | |

A diagram stores only what a user arranged: which concepts are on the canvas, where, and how
edges are routed. Which edges exist, and every label, is derived from RDF on read. The export
keeps that split: the diagrams file references concepts by IRI and `slovniky.jsonld` supplies
their content. A concept appears at most once as a node in a diagram. Nodes and edges have no IRI
of their own (blank nodes in RDF).

Row ids, the optimistic-lock `version` and the internal edge bookkeeping columns are not exported.

### Diagram IRI

Diagrams today are identified by ontology and name. Neither is stable: diagrams can be renamed, and
renaming an ontology changes its IRI. The export therefore gives every diagram its own IRI:

- New column `diagrams.iri_id` (`UUID`, `NOT NULL`, unique), set when the diagram is created.
  Liquibase `024` adds the column, backfills existing rows with `gen_random_uuid()` and then adds the
  constraint. Rollback drops the column.
- IRI = `<diagram IRI base>/<iri_id>`. The base is configuration (`ismd.export.diagram-iri-base`);
  its value depends on pending decision 2.
- The IRI survives renaming the diagram and renaming or moving its ontology. It is not reused after
  the diagram is deleted.

## How the export is built

`slovniky.jsonld`:

1. **Read PostgreSQL once.** In a single read-only transaction, load every ontology with its
   concepts into export DTOs. These DTOs have no user or comment fields, so excluded data cannot
   leak through a shared model. Record the fingerprint and `exportováno`.
2. **Write ontology by ontology.** For each ontology, call
   `OntologyDownloadService.downloadOntology(id, "json-ld")`, merge in the PostgreSQL metadata, and
   write the node to the temporary file with a streaming JSON writer. Only one ontology is held in
   memory at a time.
3. **Write the export record last** (node order in `@graph` carries no meaning), then move the file
   into place.

`diagramy.jsonld` reads only PostgreSQL (diagrams with nodes and edges, ontology IRIs) and is fast.

Design points that follow from the existing code:

- **Validation does not block the export.** The download restriction for ontologies with
  validation errors lives in `OntologyController`, not in the service, so calling the service
  directly includes every draft.
- **Cleaned content.** The service applies the same filtering and OFN transformation as the public
  download, so the export and the per-ontology download always agree.
- **Failures are reported per ontology** (`stav-obsahu = FAILED`, `úplný = false`). A build that
  fails as a whole keeps the previous cached file and the request gets `503`.
- **An empty ontology is not a failure.** A draft without RDF content is exported with its
  metadata and `stav-obsahu = EMPTY`.
- **Fuseki load.** Graph fetches run one after another and go through the existing Fuseki
  semaphore, so an export cannot starve interactive requests. The cache means a public URL cannot
  be used to trigger repeated full rebuilds: a rebuild runs only when the data has changed.

## Consistency

PostgreSQL and TDB2 share no transaction (see [`PG_TDB2_CONSISTENCY.md`](./PG_TDB2_CONSISTENCY.md)).
The PostgreSQL side of an export is one consistent snapshot; the RDF of each ontology is read
shortly afterwards. An edit made while the export is running can therefore appear in the RDF but
not in the metadata. `exportováno` marks the PostgreSQL snapshot. Such an edit changes the
fingerprint, so the next request rebuilds the file.

## Pending decisions

Forwarded to the client.

| # | Decision | Effect on the design |
|---|---|---|
| 1 | **Access and draft ontologies**: are both files public, including drafts, or are drafts left out? | The design assumes public with drafts. Published-only: one filter in the PostgreSQL read; concepts of a published ontology still need the draft/published split, which the merged `je-publikován` already gives. If the files are not public, they cannot be an NKOD distribution. |
| 2 | **Hosting of the ISMD export vocabulary and context**: where the vocabulary describing this dataset lives, where its `@context` file is served, and the base IRI for diagrams | The context must sit at a stable, public, static URL. Options: a static resource in this backend, or a repository published like OFN. The diagram IRI base follows from the same choice. |

NKOD catalogue records for the two distributions are written once by hand and are not part of this
design.
